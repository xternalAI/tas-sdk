The problem

Lock-in hides in five places

Picking an LLM-ops platform is easy. Leaving one is not, because its SDK ends up woven through your application. Trace and Scale puts one interface in front of each of the places that happens.

Where you get locked inWhat the SDK does instead
Prompts live in a vendor's UIPrompts are YAML files in your repo, synced to and from the platform with a CLI. You choose which side is the source of truth.
Vendor SDK calls across your codeOne run() call. The model, settings, tools and output schema come from the prompt, on any platform.
Tracing tied to one backendSpans are recorded once and exported as OpenTelemetry to whichever platforms you list, including two at once.
Evals written for one runnerThe task and scorers run in your process. Platforms only store the result, so numbers do not change with the vendor.
Sensitive data already sent outMasking runs in your process, before any exporter sees a span, with the same rules for every vendor.

What you get

Portable promptsOne format. Push, pull, version, label, archive. Identical round-trip on all three platforms.
One way to call modelsStructured output with validation, tool loops and chat, through any OpenAI-compatible gateway.
Tracing with maskingAutomatic spans for every run, model call and tool. Never blocks your request path by default.
Evals and experimentsDatasets, scorers, an LLM judge and CI thresholds, stored as experiments on your platform.
Multi-tenant by designEvery client is self-contained: its own platform, keys, masking rules and traces. No globals.
Two dependenciesVendor APIs are called with fetch. No vendor SDKs, no OpenTelemetry SDK. Small supply-chain surface.
Quirks are absorbed, not exposed. Each platform stores prompts differently. Where one cannot hold a field natively, the SDK keeps it in that platform's free-form metadata, so your code always gets back exactly what it pushed. Every adapter passes the same conformance suite against the real service.

Getting started

From zero to a traced model call

The package is not on npm yet. These examples are the current API of the development build.

1

Configure once

tas.config.tsimport { defineConfig, braintrust, pii } from "@traceandscale/sdk";

export default defineConfig({
  // Where prompts, traces and experiments go. Swap this line to change vendor.
  platform: braintrust({ apiKey: process.env.BRAINTRUST_API_KEY!, projectName: "support" }),
  canonical: "repo",            // which side wins on conflict: "repo" or "platform"
  promptsDir: "./prompts",
  // Any OpenAI-compatible endpoint; map prompt model ids to what it expects.
  gateway: { baseURL: process.env.GATEWAY_URL!, models: { "gpt-5": "openai/gpt-5" } },
  // Applied in-process before anything is exported.
  masking: { keys: ["authorization", /token/i], patterns: [pii.email, pii.creditCard] },
});
2

Write a prompt as a file

prompts/support/triage.prompt.yamlmodel: { id: gpt-5, params: { temperature: 0 } }
messages:
  - role: system
    content: You triage tickets for {{company}}.
  - placeholder: history            # a slot for earlier messages
  - role: user
    content: "{{ticket.body}}"
output:
  schema:
    type: object
    properties: { queue: { type: string, enum: [billing, technical] } }
    required: [queue]
3

Call it

import { createClient, loadPrompts } from "@traceandscale/sdk";
import config from "./tas.config.ts";

const tas = createClient({ ...config, prompts: await loadPrompts("./prompts") });

const result = await tas.run("support/triage", {
  variables: { company: "Acme", ticket: { body: "I was charged twice" } },
  placeholders: { history: [] },
});

result.output;   // { queue: "billing" }  parsed and validated against the prompt's schema

Prompts

Push and pull prompts like code

The CLI compares each prompt file with the platform's latest version and a lockfile, so it knows who changed what.

Terminal$ tas prompts status
in-sync         support/greeting
local-changed   support/triage
remote-changed  support/escalation
deleted-locally support/old-flow

$ tas prompts push --label production
unchanged  support/greeting    @1000198225668278133
pushed     support/triage      @1000198225687876372
pushed     support/escalation  @1000198225687901455  (overwrote remote change)
skipped    support/old-flow    (deleted here, still on the platform)

$ tas prompts pull            # bring edits made in the vendor UI back as file diffs
$ tas prompts push --profile acme-langfuse   # same repo, another tenant or vendor

You choose the source of truth

Set canonical per config. The rule is the same everywhere: the canonical side wins, and the other side never overwrites it without --force.

  • repo: files are the truth, the platform is a mirror. UI edits can still be pulled in as proposals.
  • platform: the platform is the truth, files are a snapshot used when it is unreachable.

Retire prompts safely

Add archived: true to a prompt file and push. Nothing is deleted, the SDK refuses to serve it, and removing the line restores it. Real deletion is a separate, explicit command.

Moving to another vendor

tas.config.ts// before
platform: braintrust({ apiKey, projectName }),
// after
platform: langsmith({ apiKey }),
$ tas prompts push
pushed  support/greeting
pushed  support/triage
pushed  support/escalation

Application code does not change. Model settings, tools and output schemas arrive in each platform's own native format, so prompts stay usable in the vendor's playground.

Templates that mean the same thing everywhere

The portable syntax is {{name}} and {{nested.path}}, rendered by the SDK and never by the platform. Loops, filters and vendor-only features are flagged by status, refused by push, and rejected at render time, so unrendered template code never reaches a model.

Run, trace, evaluate

The same three calls on every platform

Tools and typed output

import { z } from "zod";   // plain JSON Schema and TypeBox schemas work too

const { output } = await tas.run("support/agent", {
  variables: { question },
  output: z.object({ answer: z.string(), refund: z.boolean() }),   // output is typed from this
  tools: {
    // Declared in the prompt; give it a function and the SDK runs the loop.
    lookup_order: async ({ id }) => orders.find(id),
  },
});

Tracing with masking

await tas.trace("handle-ticket", { userId, sessionId, tags: ["beta"] }, async () => {
  const triage = await tas.run("support/triage", { variables });   // traced automatically
  return tas.run("support/reply", { variables: { ...variables, queue: triage.output.queue } });
});                                                 // spans for each run, model call and tool
  • Inputs, outputs, metadata and error text are masked in-process before export.
  • tracing: [langfuse(...), braintrust(...)] sends the same spans to both while you trial a vendor.
  • Buffered by default: your code never waits on a tracing platform. A blocking mode exists for serverless.
  • Each span carries the prompt's name and content hash, which survive a vendor switch.

Evals and experiments

evals/triage.eval.tsimport { defineEval, exactMatch, judge, loadDataset } from "@traceandscale/sdk";

export default async (tas) => defineEval({
  name: "triage-accuracy",
  data: await loadDataset("datasets/tickets.dataset.jsonl"),
  task: async (input) => (await tas.run("support/triage", { variables: input })).output,
  scorers: {
    exact: exactMatch,
    helpful: judge(tas, "judges/helpfulness"),   // an LLM judge is just another prompt
  },
  thresholds: { exact: 0.9 },                      // below this, the run fails
});
$ tas eval evals/triage.eval.ts            # exits 1 in CI when a threshold is missed
pass  triage-accuracy  120 items  exact 0.942  helpful 0.871

Where it stands today

"Works" means implemented, covered by tests, and run against the real service. Nothing here is a roadmap promise.

Not built yet

  • Streaming responses
  • Automatic retries on gateway errors
  • Pulling datasets curated in a vendor UI back into files
  • Attaching scores to live traces
  • A bridge for apps that already use OpenTelemetry
  • SDKs for languages other than TypeScript
  • Adapters beyond the first three platforms

Known limits, by design

  • Only the OpenAI chat-completions wire format is spoken.
  • Text-only messages with system, user and assistant roles. Multimodal prompts are rejected as not portable.
  • Template logic (loops, filters) is not portable and is flagged.
  • Vendor-side features stay with the vendor: online evaluators, annotation queues, playground sessions, historical traces.
In progress development. The package @traceandscale/sdk is not published yet, has had no production use, and its API can still change. Every design decision and caveat is written down and pinned by a test, so behaviour changes are deliberate and visible.
